# 調査メモ 初期表示速度比較の件

改変前Godot 4.7.1 Web版とgdweb限定版を、同一の最小2D作品とChromium条件で実測。
初期HTML表示、Wasm取得、engine初期化、GDScript起動、初回描画を個別に比較。
調査日: 2026-08-12

## 結論

静的HTMLのcold中央値はフル版104 ms、gdweb 112 ms。Wasmを待たないHTML先行表示は成立。

2D物理、音声、遅延PCK、TextServerFallback、z順・font同期、実配信fontを含むgdweb最終runtimeの初回2D描画は、cold中央値1,942.3 ms。フル版4,015.4 msから51.63%短縮。warmは698.5 ms、フル版1,442.9 msから51.59%短縮。

coldの総転送量は6,519,456 Bから2,859,505 Bへ56.14%減。gdwebはこの内、font 64,404 Bを取得。warmはHTTP cacheから全資源が命中し、転送量0 B。それでも初回描画が51.59%短いため、downloadだけでなくWasm decode、compile、Godot登録とSceneTree起動の削減も効果あり。

## 比較対象

共通条件。

- Godot 4.7.1 stable、commit `a13da4feb8d8aefc283c3763d33a2f170a18d541`
- Emscripten 4.0.11
- `target=template_release`、`threads=no`
- `optimize=size_extra`、`lto=none`、`debug_symbols=no`
- `disable_path_overrides=no`
- 同一`project.godot`、`main.tscn`、`bench.gd`
- `Node2D._draw()`で同じ緑色矩形を1個描画
- renderer設定は`gl_compatibility`。gdweb限定版は専用build分岐でdummyとCanvas 2Dへ固定

フル版は改変前commitを`.tmp/gdweb/load-benchmark/full-source/`へ別展開してbuild。module、3D、高度GUI、物理、ナビゲーション、OpenGL/WebGLを本家のまま保持。gdweb版はShader、WebGL、OpenGL、3D、ナビゲーションを排除し、限定2D物理と音声を採用。GUI配置用のTextServerFallback、FreeType、MSDFGen、z順・font同期、遅延PCKを含む最終runtime。

| 成果物 | フル版 | gdweb | 削減率 |
|---|---:|---:|---:|
| Wasm raw | 29,873,990 B | 13,970,160 B | 53.24% |
| Wasm Brotli q11 | 6,455,075 B | 2,742,902 B | 57.51% |
| JavaScript raw | 272,745 B | 205,235 B | 24.75% |
| JavaScript Brotli q11 | 59,082 B | 46,900 B | 20.62% |
| WOFF2 font raw | なし | 64,100 B | - |
| WOFF2 font配信body | なし | 64,104 B | - |
| audio worklet 2件 raw | 未観測 | 10,271 B | - |
| audio worklet 2件 Brotli q11 | 未観測 | 2,716 B | - |

速度試験は通常Godot exportの最終runtimeをバイト単位で複製して実施。fontはBrotli再圧縮でrawより4 B大きいが、本番相当の配信条件を固定するため同じBrotli q11応答を使用。

## 実行条件

- Playwright Chromium 145.0.7632.6、headless
- viewport 400×240
- CPU slowdown 4倍
- download 2,500,000 B/s、20 Mbit/s
- upload 750,000 B/s、6 Mbit/s
- 往復遅延のCDP指定40 ms
- HTTP配信はBrotli q11、`Content-Length`、`max-age=31536000, immutable`
- gdwebはWasm初期化前に`godot.font.woff2`の`document.fonts.load()`完了を待機
- coldは毎回新しいbrowser contextと`Network.setCacheDisabled=true`
- warmはvariantごとに1回先行起動後、同じcontextでHTTP cacheを使用
- coldとwarmを各7回、各variant合計28試行
- p95はnearest-rank法。7回では最大値

帯域値はChrome DevTools Protocolのbytes/s。遅延は同プロトコルの`Network.emulateNetworkConditions`に指定。

## 時間の定義

| 指標 | 観測境界 |
|---|---|
| 初期HTML | Navigation Timing起点から`first-contentful-paint` |
| Wasm取得 | Wasm resourceの`responseEnd - startTime` |
| Wasm取得完了 | Navigation Timing起点からWasm `responseEnd` |
| engine ready | `await engine.init('godot')`完了 |
| GDScript ready | `Node2D._ready()`の`BENCH_GD_READY` |
| 初回描画 | `RenderingServer.frame_post_draw`の初回signal |

GDScriptのログはページ内の`console.log`で即時捕捉し、同じ`performance.now()`時間軸へ記録。Playwright通信の往復時間は含めていない。

## 容量と時間の接続

coldではWasm Brotli bodyが6,455,075 Bから2,742,902 Bへ57.51%減。Wasm取得時間は56.56%短縮。固定帯域下で容量削減とほぼ一致。font 64,404 Bを加えた総転送量でも56.14%削減。

warmでは転送がないが、Wasm cache読取は51.42%、GDScript readyは52.04%、初回描画は51.59%短縮。限定buildは再訪時の実行コストも削減。

engine readyからGDScript readyまでの中央値は、coldフル約1,099 ms、gdweb約434 ms。warmフル約1,123 ms、gdweb約436 ms。Wasm instantiate後のclass登録、server起動、scene読込みにも大きな差。

## 限界

- 各条件7回。p95は最大値と同じで、本番SLOを決める標本数ではない
- headless Chromiumと固定エミュレーションの比較。端末別の値ではない
- 作品は矩形1個の最小場面。実作品のPCK、画像、文字数は含まない
- fontは実配信ファイルを取得したが、最小作品の文字はHTML shellの1行のみ
- audio workletは成果物に含むが、音声再生なしのため取得時間と転送量は未測定
- フル版は比較を揃えるため`threads=no`と`size_extra`。公式配布templateのバイナリそのものではない
- 起動中のメモリ量、main thread占有時間、long task、実ページのDOM要素数は未測定

## 判断

HTMLと文字を先行配信する設計なら、エンジンWasmの大きさは初期HTML表示を遅らせない。一方、作品の操作可能化と初回描画には直結。

gdweb限定buildは、今回の固定条件でcoldとwarmの初回描画時間を約半分へ短縮。共通URLの長期cacheと組み合わせ、初期HTML表示後に必要な場面だけengineを起動する構成を採用候補とする根拠。

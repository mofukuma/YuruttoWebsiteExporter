# 調査メモ 近縁プロジェクトの件

Godot編集物をWebGLなしのHTML、CSS、Canvas 2Dへ出す既存実装の確認。
調査日: 2026-08-12

## 結論

同じ目的、同じ入力、同じ制約を満たす成熟プロジェクトは未発見。

近い要素は別々のプロジェクトに存在。

- Godotを別Wasmホストへ移すplatform分離
- DOMを2D要素として動かすエンジン
- Canvas 2D専用または代替描画
- 小型2Dランタイム

## 比較

| プロジェクト | 近い点 | 不一致 | 採用する知見 |
|---|---|---|---|
| wasmcart-godot | Godotを独立platformへ移植。GDScript VMとPCKを維持 | GLES3必須。約23MiB級Wasmの先例で軽量Web目的とは不一致 | platform境界、main loop、入力・音声の置換単位 |
| Crafty | 2D EntityをDOMで描画。Canvas層も保有 | JavaScript API。Godot場面・GDScript非対応 | DOM要素とCanvas層の併用、2D属性の差分更新 |
| Excalibur | 描画抽象がありCanvas 2Dへ切替可能 | 既定はWebGL。TypeScript API | 描画先抽象、対応外効果の明示、基準場面比較 |
| Kontra.js | js13k向け小型Canvas 2Dライブラリー | Godot互換なし。Wasmなし | 機能を選択式にする小型化思想 |
| LittleJS | 小型2D、Canvas 2D、物理・入力の実装例 | WebGLとの混成が中心。Godot互換なし | 小型2D API、Canvas 2D経路の試験例 |
| dotLottie-web | Wasm + Canvas 2D + Worker + OffscreenCanvas | Lottie再生専用 | WasmとCanvas 2Dの分業、Workerを任意高速化にする方式 |

## 詳細

### wasmcart-godot

[wasmcart-godot](https://github.com/wasmcart/wasmcart-godot)はGodot 4を単独Wasmへ移し、同じランタイムへ別PCKを組み合わせる実装。`platform/wasmcart`へOS、Display、Audio、入口、ファイルシステムを閉じ込める構成。

GDScript VMは純粋なバイトコード解釈器でplatform依存がなく、Godot main loopもフレーム単位のため移植しやすいという分析。[設計資料](https://github.com/wasmcart/wasmcart-godot/blob/main/PLAN.md#L217-L285)

一方、描画はGLES3のGL呼び出しをホストへ渡す方式。完成説明でもGLを明記。[README](https://github.com/wasmcart/wasmcart-godot#what-works)

適用。

- `platform/web`を直接肥大化させず、gdweb固有層へ閉じ込める
- main loop、入力、音声、資産を独立した主機能に分ける
- GDScript VMのplatform非依存部分を調査対象にする

不採用。

- GLES3 bridge
- フルGodot runtime
- 単一PCK

### Crafty

[Crafty](https://github.com/craftyjs/Crafty)は2D Entityへ`DOM`、`Canvas`などの描画部品を付与するJavaScriptエンジン。READMEのPong例でも各2D要素をDOMとして動かす構成。

[DOM API](https://craftyjs.com/api/DOM.html)とCanvas APIが分かれ、同じ2Dモデルへ複数の描画経路を持つ点が最も近い。

適用。

- Nodeごとに描画先を選ぶ
- DOM向きとCanvas向きの型を分ける
- 描画先に依存しない場面状態

注意。Craftyは古いブラウザーも意識した設計。現在のCSS containment、OffscreenCanvas、Wasm連携は別途設計が必要。

### Excalibur

[Excalibur Graphics Context](https://excaliburjs.com/docs/graphics-context/)は既定WebGLからCanvas 2Dへ切替可能。Canvas 2Dでは後処理や独自rendererなど一部機能が使えないことを明示。

適用。

- 描画抽象の上で機能対応を表にする
- 対応不能な効果を無言で近似しない
- 同一基準場面を描画先ごとに検証

### Kontra.js

[Kontra.js](https://github.com/straker/kontra)はjs13kGames向けの小型JavaScriptゲーム部品。機能を必要な分だけ選ぶ思想が初期サイズ削減の参考。

適用。gdweb runtimeも大きな汎用API一式ではなく、書き出し器が利用機能を確定し、不要命令とホスト関数をリンクしない構成。

### LittleJS

[LittleJS](https://github.com/KilledByAPixel/LittleJS)は小型2DエンジンでCanvas 2D経路、入力、音声、物理、TileMap、粒子の実例を持つ。主経路はWebGL 2との混成なのでコードの直接採用候補ではない。

適用。Canvas 2Dで成立する2D機能の範囲、ストレス場面、TileMapや粒子の段階追加順。

### dotLottie-web

[dotLottie-web](https://github.com/LottieFiles/dotlottie-web)はWasm、Canvas 2D、Fetchを必須とし、WorkerとOffscreenCanvasを任意高速化として扱う。

適用。初期版をmain threadとCanvas 2Dで成立させ、Workerを必須条件にしない。DOM更新はmain threadに残し、Canvas専用処理だけ後から分離。

## GitHub検索

次の語でrepository検索。

- `gdscript wasm`
- `godot html css dom`
- `godot canvas2d renderer`
- `godot web lightweight`

`godot-wasm`はGodotから別Wasm moduleを呼ぶ拡張で、GDScriptをWasmへ変換するものではない。Web出力も未対応。[godot-wasm](https://github.com/ashtonmeuser/godot-wasm)

`wasmcart-godot`は近い移植例だがGL必須。Godot場面とGDScriptをブラウザーのDOM・Canvas 2Dへ出す実装ではない。

## 判断

既存ライブラリーの組合せではGodotの意味とGDScriptを保てない。gdweb固有の書き出し器とVMが必要。

参照する設計は三点。

1. wasmcart-godotのplatform分離
2. CraftyのDOM・Canvas併用
3. 小型2Dエンジンの機能選択と容量試験

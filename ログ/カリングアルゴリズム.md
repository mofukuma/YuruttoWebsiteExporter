# カリングアルゴリズム

## なにを解きたいか

文字はHTMLとして本物の要素で置いている。だから検索にも出るし、選んでコピーもできる。
その代わり、文字の数が増えると要素の数もそのまま増える。

要素が増えて困るのは、毎frameの更新のとき。Godot側が文字の位置を決め直すたびに、
その数だけJavaScriptとBrowserの仕事が積み上がる。画面に映っていない文字にも同じ手間がかかる。

だから「いま見えていないものは触らない」を入れたい。これがカリング。

見えていない理由は二つある。どちらも扱う。

- 画面の外にある。Godotの画面より外側へ出ている文字
- ブラウザのスクロールで外れている。作品が縦に長いページの一部として置かれている場合

## いまの作りと、どこへ足すか

いまは `library_yweb_text.js` の `place` が、要素ごとに `transform` を書き込んでいる。
文字が増えるとこの書き込みが増える。カリングはこの手前へ置く。

`place` を呼ぶ前に「この要素はいま見える範囲にいるか」を判定し、見えないものは
書き込みごと省く。省いた要素は `display:none` にして、Browserのレイアウトと描画の
対象からも外す。

## 三つの層で削る

一段で全部やろうとせず、安いものから順に当てる。

### 一層目: 作品そのものが画面に無いとき、まるごと止める

作品が縦長ページの途中に置かれていて、スクロールで完全に外れているなら、
文字の同期は一切いらない。canvasを覆うroot要素を一つだけ見張れば判定できる。

`IntersectionObserver` をroot要素へ一つ付ける。外れたら同期をまるごと休み、
戻ったら再開する。要素が何個あっても観測対象は一つなので、これが一番安い。

```js
// 作品が画面から外れている間は、文字の同期そのものを休ませる。
const gate = new IntersectionObserver((entries) => {
	YWebText.onScreen = entries[0].isIntersecting;
}, { rootMargin: '200px' }); // 少し手前から起こして、戻ったとき間に合わせる。
gate.observe(YWebText.getRoot());
```

`rootMargin` を足すのは、画面へ入りきってから起こすと一frame遅れて見えるため。
少し手前から準備する。

### 二層目: 作品の中で、画面の外へ出ている文字を落とす

Godotの画面の中の話。文字の矩形はGodot側が既に持っているので、
その矩形と画面の矩形が重なるかを見るだけで判定できる。これは掛け算の要らない比較四回で済む。

```js
// Godot画面の矩形と重ならない文字は、置き直しも描画もしない。
function visible(x, y, w, h, viewW, viewH, margin) {
	return x + w >= -margin && y + h >= -margin && x <= viewW + margin && y <= viewH + margin;
}
```

ここで大事なのは、判定に `getBoundingClientRect()` を使わないこと。
あれはBrowserへレイアウトの確定を要求するので、要素ごとに呼ぶと遅くなる。
Godotが既に知っている数値だけで判定する。

### 三層目: スクロールで外れた文字を、CSSへ任せる

作品が画面に入っていても、その一部だけがスクロールで切れていることがある。
ここは自前で数えず、CSSの `content-visibility: auto` へ任せられる。
画面の外にある間、Browserがその要素の中身の描画とレイアウトを省いてくれる。

```css
/* 画面の外にある文字は、Browserの判断で中身の描画を省く。 */
.yweb-text {
	content-visibility: auto;
	contain-intrinsic-size: auto 1em; /* 省いている間の大きさの見積り。 */
}
```

`contain-intrinsic-size` を必ず添える。これが無いと、省いた要素の大きさが0として
扱われ、ページ全体の高さが変わってスクロール位置が動いてしまう。

手元のChromiumで確かめた。画面の外にある `content-visibility:auto` の文字は、
`textContent` からも `innerText` からも読めたままだった。
つまり検索と選択と読み上げは効いたまま、描画の手間だけが省ける。
これがこの仕組みを選ぶ理由。

一方で、そのときの高さは `contain-intrinsic-size` で書いた見積り(40px)が返り、
本当の高さ(24px)ではなかった。位置の計算にこの値を使わないこと。

## 判定の順番と、そのわけ

```
作品が画面外か  ──はい──> なにもしない(観測対象は1つ)
      │いいえ
      ▼
画面の矩形と重なるか ──いいえ──> display:none にして置き直しを省く
      │はい
      ▼
transformを書き込む ──> あとはcontent-visibilityへ任せる
```

安いものから当てる。一層目は要素数に関係なく一定。二層目は要素数に比例するが、
比較だけなので軽い。重い書き込みは、そこを通り抜けたものだけが受ける。

## 要素をどう隠すか

隠しかたで費用が変わる。使い分ける。

| やりかた | 費用 | 使うところ |
|---|---|---|
| `display:none` | レイアウトからも外れる。戻すとき組み直しが要る | 画面の外にある文字 |
| `visibility:hidden` | 場所は取ったまま。戻すのが軽い | 一瞬だけ消すもの |
| 要素を消す | 一番安くなるが、選択とコピーの対象からも消える | 使わない |

要素そのものを消すのは選ばない。文字がHTMLとして在ることが、この仕組みの目的だから。
検索や読み上げから消えてしまっては本末転倒になる。

## 数が多いときの探しかた

文字が数百を超えたら、全部を毎frame見比べるのも無駄になる。
そのときは画面を格子に区切って、格子ごとに文字を登録する。

画面を例えば8×8に割り、それぞれの文字がどの升目にいるかを覚えておく。
判定のときは、見えている升目に登録された文字だけを見る。

格子を選ぶ理由は、文字の大きさが揃っていて、画面という決まった広さへ収まるから。
四分木は大きさがばらつくものに向くが、ここでは升目のほうが実装も更新も単純で速い。

ただしこれは、実際に数百個を超えて遅くなってから入れる。
文字が数十個の作品では、素直に全部見比べるほうが速い。

## 確かめかた

同じ作品で、カリングのありなしを比べる。

- 文字を200個置いた作品を用意する
- そのうち画面に映るのは20個くらいにする
- 毎frameの `place` の呼び出し回数を数える
- スクロールで作品を画面外へ出し、同期が止まることを見る

数が減っていることと、見えている文字の位置が今までどおりであることの両方を見る。
速くなっても文字の位置がずれたら意味がない。

## 気をつけること

`IntersectionObserver` の通知は、すぐには来ない。次の描画の機会まで待たされる。
だから「いま見えているか」を毎frameの判定へ直接使わない。
一層目の休止判定のように、少し遅れても困らないところへ使う。

画面の中の判定は、遅れの無いGodot側の数値で行う。役割を分ける。
